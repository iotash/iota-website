A release about what iota's tools may touch without asking you. **Reading is
no longer confined to the project; a write outside it is now asked about
instead of refused**, and the directories the model may write to outside the
project are one top-level list, `write_roots:`, shared by the file tools and
the shell. Three changes need something from you: **`tools.shell.write` is
gone**, **MCP tools ask before every call** unless you mark the server
`auto_run`, and **a repository's `.iota.yaml` is used only once you trust
it**. iota's own config and your git hooks are now off limits to its tools.

## Upgrading

- **`tools.shell.write` → `write_roots:`.** A config that still has
  `tools.shell.write` loses the shell tool, with a warning. Move the list to
  the top level; the file tools now use it too:

  ```yaml
  write_roots: [~/notes, ../shared]   # ~ is your home; relative is from the project
  ```

- **MCP tools ask before they run.** Every call of an MCP tool is now put to
  you, like a file edit or a shell command, and in a `-m` run a call to a
  server without `auto_run` is refused, naming the server and the key. For a
  server you trust to run unasked:

  ```yaml
  mcp_servers:
    db:
      auto_run: true   # the default is false
  ```

  A `--mcp` server always asks, so `-m … --mcp …` can no longer run its
  tools: write it as an `mcp_servers` entry with `auto_run: true` instead.

- **A repository's `.iota.yaml` must be trusted.** On a terminal iota shows
  what the file would do and asks once. A run with no terminal — `-m`, a
  script, CI, a bot — never asks: it skips the file with one warning and runs
  on `~/.iota.yaml` alone. For those, run `iota config trust` in the
  directory once, or name the file with `-c <file>`, which is always used.

- **Some git commands fail inside the sandbox.** `git config`,
  `git remote add`, `git init`, `git push -u`, `git submodule add` and hook
  installers (husky, pre-commit, lefthook) need to write files that are now
  protected (below). Run them yourself, or let iota run them with
  `sandbox: off`, where each command is asked about.

- **The model can no longer run `iota config trust`, `config untrust`,
  `config init`, `mcp add` or `mcp remove` for you.** It asks you to run them
  in your own terminal, where they work as before.

## Added

- **`write_roots:` opens directories outside the project.** A top-level list
  of directories that both the file tools and a sandboxed shell may write. A
  blank entry is an error, and the model is told the list, so it knows where
  it may write before it tries.
- **A write outside the project can be approved.** When the model edits or
  writes a file outside the project and `write_roots:`, iota asks instead of
  refusing. The prompt shows where the file really is, symlinks followed, and
  is marked `(outside the project root)`; it asks even with
  `tools.code.auto_write`. "Allow for this session" covers that one directory
  through that one tool. In a `-m` run such a write is refused and the
  message says to add the directory to `write_roots:`.
- **`outside_writes: ask | refuse`.** `ask` is the default; `refuse` keeps
  the old rule — writes outside the roots fail with no prompt. A later config
  file cannot loosen a `refuse` set by an earlier one.
- **`iota config trust` and `iota config untrust`** record and forget a
  project's `.iota.yaml`. Editing a trusted file asks again.

## Changed

- **Reading is no longer restricted to the project.** `read_file`,
  `list_dir`, `glob` and `grep` read any path and follow a symlink wherever it
  leads. The shell could already read the whole machine unasked, so the old
  limit only pushed the model into `cat`, where you see less of what it
  reads. A search stops after 100 000 files and folders (a grep also after
  256 MB read), saying so, and Esc stops it at once (`[search cancelled]`).
- **MCP tools ask before they run.** A configured server's tools used to run
  unasked, in a chat and in `-m` alike, while the server itself is not
  sandboxed. "Allow for this session" covers one tool; the server's other
  tools still ask. iota does not guess which tools are safe from their names.
- **A repository's `.iota.yaml` must be trusted before it is used.** The file
  can start MCP servers, send a provider — and your key — somewhere else and
  loosen the sandbox, so running iota in a directory no longer means using
  it. `iota mcp list --probe` lists an untrusted file's servers without
  starting them, and `iota mcp login` refuses to log in to one.
- **iota's own config and your git hooks are off limits to its tools.** No
  sandboxed command and no file edit writes the project's `.iota.yaml`,
  `.git/hooks`, `.git/config` (submodules' and the main repository's of a
  worktree included), `~/.iota.yaml` or the list of trusted projects without
  asking, and `.git` and `~/.iota` cannot be renamed or replaced. In the
  sandbox such a write fails like any denied write; the file tools ask every
  time — even with `auto_write: true` or after "Allow for this session" —
  offering only "Allow once" and "Deny". `git add`, `commit`, `checkout` and
  `fetch` still work. On Linux the sandbox protects only files that exist, so
  a sandboxed command can still create a missing `.iota.yaml`.
- **"Allow for this session" ends with the conversation.** Every session
  grant is forgotten at `/new` or a `/session` resume; it used to last until
  iota exited.
- **The approval prompt says what it is asking.** It reads
  `<tool> — allow?` instead of saying every call "wants to modify files", and
  the notification herdr or the terminal bell gets reads
  `<tool> needs approval`.
- **The model knows what the sandbox looks like.** It is told that a shell
  command failing with `Operation not permitted`, `Read-only file system` or
  no network was stopped by the sandbox, and no longer that every write
  outside the project is stopped.

## Fixed

- **The file tools check where a symlink really leads.** A link inside the
  project that points outside it was followed as if it were part of the
  project; writing through it is now a write outside the project — asked, or
  refused under `outside_writes: refuse`.
