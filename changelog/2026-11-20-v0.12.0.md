A release about what you allow. **An approval can now be kept for the session
or for the project**, for a directory, a built-in tool or an MCP tool, and a
resumed session keeps what you allowed in it. **`/allow` grants the same by
hand**, and a bare `/allow` opens a panel with `Add`, `Grants` and `Static`
tabs, where grants are also taken back. **`--add-dir` makes a directory
writable for one run**, without a config file.

## Added

- **Allowing a write outside the project makes its directory writable.** The
  approval prompt offers `Allow, and make <dir> writable for this session` and
  `… for this project`: the directory and everything under it become writable
  by `edit_file`, `write_file` and sandboxed `shell` commands, with
  `tools.code.auto_write` deciding whether those writes are asked. A project
  grant lasts across `/new`, `--no-save` chats and `iota run -m` runs, and is
  kept in `~/.iota/sessions/projects/<project>/grants.json`. The prompt never
  offers `/`, your home directory or a directory above it, and `.git/hooks`
  and `.git/config` stay read-only.
- **A built-in tool can be allowed for the project.** The prompt for `shell`,
  `edit_file` or `write_file` also offers `Allow for this project`: in this
  repository, in every session and in `-m` runs, iota stops asking for it.
- **An MCP tool can be allowed for a session or a project, one tool or a
  whole server.** Its prompt offers `Always allow <server>:<tool> in this
  session` and `… in this project`; `<server>:*` covers every tool of the
  server, including ones it adds later. A project grant lets `iota run -m`
  call the tool. A server given with `--mcp` can be allowed this way too, by
  its URL or command.
- **`/allow` grants by hand.** `/allow <dir>`, `/allow shell` and
  `/allow <server>:<tool>` grant for the session; `/allow project …` for the
  project. It refuses a name it does not know or a tool that never asks. A
  message sent to the chat from another process cannot run it.
- **A bare `/allow` opens two tabs, `Add` and `Grants`.** `Add` browses
  directories from the project root and makes the chosen one writable for the
  session. `Grants` lists every grant with its level; check some with Space
  and press Enter to take them back from the session and the project at once.
  A third tab, `Static`, lists what `write_roots:` and `--add-dir` make
  writable; nothing there can be revoked. This replaces `/revoke`, which is
  gone.
- **A resumed session keeps what you allowed in it.** Session grants are saved
  with the session, so `iota resume`, `iota resume <id> -m` and a `/session`
  switch bring them back; `/new` starts with none.
- **`--add-dir <dir>` makes a directory writable for one run.** `iota run` and
  `iota resume` take it, repeatable, beside the config's `write_roots:`. A
  relative path is taken from the directory you run iota in; a resumed session
  does not remember it.
- **iota follows a dark/light switch without a restart.** The highlighted
  row of a list, a panel's input field, code blocks and diffs take the new
  shades when the window regains focus or the next turn starts; text already
  on screen keeps its shades. A terminal that does not report its background
  keeps the shades it started with.

## Fixed

- **An `iota` the model runs with `-c`, `--config` or `--mcp` stays in the
  sandbox.** It was let out like any other `iota` call, so a config the model
  wrote could turn the sandbox off.
- **No command or tool can write iota's saved sessions.** `~/.iota/sessions`
  is protected like the trust record, even when iota runs in your home
  directory or `~` is a writable root.
- **A copy reaches the clipboard of the machine you are sitting at.** Outside
  tmux, a selection goes both to the local clipboard tool and to the terminal
  (OSC 52), and the status row says which way it went. Inside GNU screen the
  sequence is wrapped so screen passes it on.
- **The first key typed is no longer lost on a terminal that answers no
  queries.**
- **iota no longer exits at once on macOS when its input is not a terminal.**
